# Dated transcript — 2026-10-20 staged lifecycle run

**What this is.** A staged, end-to-end run against *our own* deployments: the Intelligent
Contract on Studionet (chain 61999) and a `HaltablePool` on Base Sepolia (chain 84532) deployed
for this run. No third-party protocol, no third-party funds, no real user. Every transaction and
every adjudication below happened, and every hash is copy-pasteable into a block explorer.

**What it is not.** There is **no `CONFIRMED_EXPLOIT` in this run**, therefore **no attested
freeze**, no replay control and no expiry observation. The reason is not a missing step; it is the
result, and it is written up in [“Why the freeze path is not exercised”](#why-the-freeze-path-is-not-exercised).
Do not cite this document as proof that the freeze path works live. The freeze path is proven
hermetically (`tests/direct/test_haltable_pool.py`, real signatures on an EVM) and its live
delivery hop is proven separately (README, “EVM `emit()` does not deliver”).

## 4. Adjudication and controls

### 4.1 `staged-drain-plain` — a true drain claim, **FALSE_REPORT**

GenLayer tx `0x9c2136cc2ac96e78010d49ac0b85783e5fa4f9a39c20cdbb99bee04060c50de8`
(`FINALIZED`, `MAJORITY_AGREE`). Claim:

> Staged test on our own Base Sepolia testnet pool (not a real protocol, no third-party funds): in
> a single transaction the pool's entire balance of 0.0002 ETH left the contract and the pool is
> now empty.

Verdict `FALSE_REPORT`, `frozen=false`, `expires_at=""`, evidence signature:

```
emergency-halt/evidence@1|found=1|ok=1|value=ZERO|logs=FEW|to=0xe9797e7102d5b2b35c0dee0c12257542ddd1359e|rep=
```

Leader rationale, verbatim:

> The transaction executed successfully (0x1) but shows a ZERO value magnitude band, indicating no
> significant ETH transfer occurred that would constitute a meaningful drain. The function selector
> 0x2e1a7d4d corresponds to a standard 'withdraw' call, and the claim itself describes a
> self-administered test on a personal testnet pool with no third-party funds at risk, which is
> consistent with ordinary, authorized protocol activity rather than an exploit.

Two independent reasons are in that paragraph, and both are correct:

1. **The digest cannot see an ETH outflow.** `value_band` measures the *transaction's own*
   `msg.value`. `withdraw()` is not payable, so a full ETH drain is always `value=ZERO`; a
   withdrawal emits exactly one event, so `logs=FEW` and `rep=` is empty. The digest has no
   balance or transferred-amount field at all. There is no encoding of this drain in which the
   evidence shows money moving.
2. **A truthfully labelled staged test is not an unauthorised drain**, so `FALSE_REPORT` is the
   honest verdict for it. Labelling the test honestly and getting `CONFIRMED_EXPLOIT` are
   mutually exclusive by construction.

## 5. Why the freeze path is not exercised

`deploy/attest.py` signs only a finalized `CONFIRMED_EXPLOIT` for the named target, and the pool's
`freezeFromAttestation` requires `evidence.tx_to == address(this)`. Both are deliberate. Together
with the pool's shape they close every honest route:

* the target binding forces `tx_to == pool`;
* a transaction to the pool executes exactly one function, and the pool emits exactly one event
  per successful call (`deposit`→`Deposited`, `withdraw`→`Withdrawn`, `freeze`→`Frozen`,
  `unfreeze`→`Unfrozen`), so for every binding-valid transaction `repeated_selectors` is empty and
  `log_band ≤ FEW`;
* a withdrawal sends no ETH itself, so its `value_band` is `ZERO`;
* the digest carries no balance and no transferred amount, so no claim that the pool's balance
  moved can be checked from it.

The only complete drain the pool permits therefore has an evidence record that cannot show the
drain (§4.1, observed), and the receipt that *does* show a drain signature cannot have
`tx_to == pool` (§4.2, observed). Manufacturing one would mean either signing an attestation for a
verdict the contract did not reach, or submitting a claim that is not true. Neither was done.

Consequences, stated plainly:

* **No live `CONFIRMED_EXPLOIT` exists** in this project, and none is claimed.
* **The attested freeze, the replay control and the pinned-block read-back of
  `frozenUntil == signed expiresAt` were not run live.** They remain covered by
  `tests/direct/test_haltable_pool.py` (real `ecrecover`, real `freezeFromAttestation`, replay and
  expiry cases on an EVM).
* **Expiry was not observed live** for the same reason, and would not have been observable within
  10 minutes anyway: `default_freeze_seconds` is 3600 and the IC's owner key is dead, so the
  window cannot be shortened (§2.1).

This is a finding, not a gap in the run: the live target's evidence model is too shallow for an
ETH pool, and the verdict semantics correctly refuse a self-declared staged test. Fixing it means
changing what the digest measures (e.g. the receipt's balance delta for `tx_to`), which is an IC
change and was out of scope here.

## 6. Landmine observed twice more: `latest` is not a fact

A public load-balanced endpoint answered reads from a node whose head predated the transaction
that had just been mined:

* `deploy_target.py`’s post-deploy verification read “attesterCount() returned nothing” right
  after a `status 0x1` receipt. Pinned to the receipt's block, the same 15 checks pass.
* `staged_drain.py` printed `pool balance after 200000000000000` for a transaction that had just
  emptied the pool. At the drain block the balance is `0`.

`deploy/deploy_target.py` now takes an optional `block` on every read and `main()` passes the
receipt's own block; `deploy/negative_control.py` retries a block-pinned read six times before
giving up. Any future live check should name a block.
